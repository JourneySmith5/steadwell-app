# Steadwell — Client System

This is the first build of Steadwell's client-facing app, following the build order in `Steadwell_MVP_Blueprint.md` (§13). **All 14 steps of that blueprint's build order are genuinely implemented and working** — real database, real auth, real 2FA (with real account lockout after repeated failed attempts), a real application-to-client pipeline, a real agreement-acceptance gate, real Stripe checkout/discount-code/webhook code (it runs in a clearly-labeled test mode until you add Stripe keys — see below), a real, fully functional Foundation Intake (§4) covering every financial data section including real Statements file upload/storage (Vercel Blob — see below), a real, fully functional Plan Builder (§5–§8) — Coach builds the plan across Baseline, Cash-Flow Allocation, Debt Strategy, Savings & Goals, Stress Test, and Finalize stages, and the client sees the finalized plan in the portal and as a downloadable PDF — real Meetings, recurring Accountability, and Billing (§9, §11) — self-service tier enrollment/change/cancellation with real Stripe subscription integration (test-mode fallback, same as the Foundation fee), and Coach-logged meetings the client sees a filtered view of — a real Offboarding export/reminder/deletion pipeline (§16, §18, §20, §21) — a real data-export PDF, automatically-sent reminder emails, and a genuine hard-delete job — and, closing out the build order, a real Attention Queue, account lockout, an on-demand full database backup, and a server-side validation hardening pass (§11, §14), all covered below. That doesn't mean every rough edge is gone — read "What's a dev stand-in" and "Before this goes live" below for exactly what's still a simplification and what a real launch still needs.

Read this whole file before showing this to anyone — it tells you exactly what you can trust and what you can't yet.

## What's actually real

- **Public application** (`/apply`) — the full §3 intake form, writes a real lead record.
- **Coach login + required 2FA** (§2) — password + TOTP (Google Authenticator / Authy / etc.), enforced, not optional.
- **Coach review & decision** — approve/decline an applicant. Both actions open an editable email draft that a human has to review and click Send — nothing auto-sends (§21).
- **Engagement agreement acceptance gate** (§17) — after approval, the client gets a real secure link (`/agreement/[token]`) to a page rendering the actual agreement text, where they type their full name and check a box to accept — a clickwrap e-signature recorded with the agreement version, timestamp, and IP address. Checkout isn't reachable until this happens.
- **Discount codes** (§9) — two kinds. Ordinary manual codes are added freely (and toggled on/off, edited) by the coach at `/coach/settings/discount-codes`; applying one on the Foundation checkout page recalculates the real price and the real amount charged. THANKYOU15 and BIRTHDAY20 are conditional/automatic codes — nothing ever types them in (`src/lib/promotions.ts`). THANKYOU15 auto-applies to a client's first 3 Accountability billing cycles (a real Stripe Coupon, `duration: 'repeating'`) if they enroll within 24 hours of Coach sending the "Foundation Review complete" email with their plan PDF attached (`/coach/clients/[id]/meetings` → "Mark Complete & Email Plan"). BIRTHDAY20 auto-applies during a client's birth month — to the one-time Foundation fee if their date of birth happens to be on file by then (collected on Foundation Intake → Household; realistically it usually isn't yet, since that payment happens before Intake), and to an active Accountability subscription via a daily sweep (`src/lib/birthdayDiscount.ts`, riding along on the same cron as Offboarding — see below). All applicable codes stack additively (percentages just add, capped at 100% off) — one manually-typed code plus whichever automatic codes are currently eligible; Stripe's native multi-discount support (`discounts: [...]` on a subscription) does the actual combining for Accountability so THANKYOU15's 3-month run and BIRTHDAY20's single cycle each keep their own correct lifetime rather than being merged into one coupon. The "Add a New Code" form has a **"One-time code"** checkbox for generating a single-use code at will, for any name and percentage Coach types in — checked, what's typed into "Code" becomes a prefix (e.g. `HOLIDAY25` → `HOLIDAY25-X7K2Q`, `generateOneTimeCode` in `src/lib/repo/discountCodes.ts`) instead of the literal code, `max_redemptions` is set to 1, and the result is enabled immediately instead of added disabled — no separate toggle-on-then-remember-to-toggle-off step, and every one-time code shows up in its own "One-Time Codes" list further up the page as Available/Used. This replaced FAMILY90, FRIENDS50, and CHARITY100 — three shared promo codes (90%/50%/100% off) that used to sit in the regular code list and could be enabled for every checkout at once by accident; Journey had them hard-deleted (`schema.sql`'s retirement migration) rather than just disabled, specifically so they can never come back. The redemption itself is counted in `fulfillFoundationPayment` (`src/lib/checkout.ts`) the moment a payment actually completes — never at checkout start, so a client typing a code and abandoning checkout doesn't burn it.
- **Stripe checkout, payment state, and webhook handling** (§9) — `src/lib/checkout.ts` creates a real Stripe Checkout Session and `src/app/api/webhooks/stripe/route.ts` is a real, signature-verified webhook handler for `checkout.session.completed`. **This is genuine Stripe integration code, not a stand-in** — it just doesn't run against the real Stripe API until `STRIPE_SECRET_KEY` is set (see "Before this goes live"). Until then, the checkout flow automatically falls back to a page clearly marked "Test Mode — Stripe not configured, no real charge will happen," which drives the exact same payment-state and fulfillment code (`fulfillFoundationPayment`) that the real webhook calls — so nothing about the pipeline logic changes once you add real keys, only how the money actually moves.
- **Payment → account creation → client 2FA** — once payment succeeds (real or test-mode), the client accepts an invite, sets a password, verifies email, and enables required 2FA, same as the coach.
- **Status pipeline** — every stage change (`applied` → ... → `graduated`/`canceled`/`closed`) is recorded as a timeline event you can see on the client's detail page.
- **The Accountability-or-Graduate decision** (new business rule, see the blueprint's §1 and §8 for the full reasoning) — once a plan is marked finalized, the client is immediately prompted to either pick an Accountability tier or confirm they're done. There's no grace period: confirming "I'm done" sets status to Graduated and starts a real 30-day deletion countdown, which the client's Account page displays for real (it's reading an actual stored deletion date, not a placeholder). Choosing a tier instead is equally real now — see the Meetings/Accountability/Billing bullet below.
- **Required 2FA, session handling, and role-gating** — every coach and client page checks who's logged in and what stage they're allowed to be at server-side (see `src/lib/dal.ts`), not just in the UI.
- **Foundation Intake** (§4, `/portal/foundation`) — the full financial-picture intake: Household, Income (with per-source normalized-monthly calculation for variable pay), Accounts, Regular Bills (with monthly-equivalent calculation), Debt (with running totals), Emergency Fund, Savings, Sinking Funds, and Financial Goals. Every section is a real add/edit/delete form backed by its own table (see `src/lib/db/schema.sql`), autosaves as you go (no explicit "save the whole form" step), and enforces the one real submission rule from the blueprint — at least one Financial Goal before you can submit. Submitting locks every section read-only for Coach's review; "Request an Update" reopens it. Coach sees the submitted status on the client's detail page.
- **Plan Builder** (§5–§8, `/coach/clients/[id]/plan`) — once Foundation Intake is submitted, Coach works through seven real stages: **Baseline** (income/bills/debt-minimums pulled from Foundation Intake, plus Coach's own estimate of typical additional spending — the Baseline stage's "Documents" panel shows both Statements and anything the client has attached to a message (see the messaging bullet above), so Coach doesn't have to leave the Plan Builder to go check the Messages thread, but this figure is still Coach-entered rather than computed from them, a reasonable next step rather than day-one scope — computing a real Available Monthly Cash Flow); **Stability** (read-only context: income stability, EF gap, upcoming sinking funds); **Cash-Flow Allocation Workspace** (§6) — Coach sets planned amounts for flexible living-expense categories, the Emergency Fund, and Sinking Funds directly, while Debt Acceleration and Financial Goals totals are derived from the Debt Strategy and Savings & Goals stages so there's one source of truth, with a running Planned Income vs. Planned Outflow balance check; **Debt Strategy** — a strategy (Avalanche/Snowball/Hybrid/Custom) and planned payment per debt, with a real month-by-month amortization simulation computing months-to-payoff and total interest, plus computed (not free-text) insights like "highest APR" or "promo rate expiring soon"; **Savings & Goals** — planned monthly amount per goal with a real projected-completion-date calculation and computed underfunded-vs-deadline insights; **Stress Test** (§8) — recompute the plan with one or more income sources excluded, to see the real shortfall; **Finalize** — add First-30-Days action items, then Mark Reviewed → Finalize Plan (blocked until the balance check is exactly $0) → Present Plan to Client. Once presented, the client sees the same plan — Starting Point, Monthly Plan, Debt Strategy, Emergency Fund, Sinking Funds, Financial Goals, First 30 Days — at `/portal/plan`, plus a real on-demand PDF download (`/portal/plan/pdf`, built with `pdfkit`) generated from the same finalized, immutable data.
- **Meetings, recurring Accountability, and Billing** (§9, §11, `/portal/accountability`, `/portal/billing`, `/coach/clients/[id]/meetings`) — after the plan is presented, the client can self-service enroll in an Accountability tier (Steady/Momentum/Intensive), change tiers, or cancel — all real Stripe subscription integration (`src/lib/accountability.ts`), no Coach approval step, exactly as the blueprint specifies. It's the same Stripe-configured/test-mode fork as the Foundation fee: with real keys, it creates an actual Stripe subscription Checkout Session and a real Billing Portal link for payment-method management; without them, a clearly-labeled test-mode path drives the exact same `fulfillAccountabilityEnrollment` function the real webhook calls. Canceling triggers Offboarding (§16) the same way declining Accountability or Coach closing a record does — one status-change event, uniform downstream handling. Coach logs meetings (Foundation or Accountability, status, private notes, client-facing action items, next meeting date) from a client's Meetings page — Google Calendar's Appointment Schedule handles the actual booking UX (§1a, explicitly not rebuilt — see §14), this just tracks status/notes/action items "where practical," same wording as the blueprint. The client's Accountability page shows their tier, meeting history, and action items — never Coach's private notes. For scheduled Accountability meetings, the client can also add their own progress notes there ("what I've done since last time") that Coach sees on the same client's Meetings page before the call; a daily sweep (`src/lib/meetingReminders.ts`, riding along on the Offboarding cron — see below) auto-sends an "add your progress notes" reminder email 48 hours and 24 hours before the meeting date (calendar-day precision, since only a date — not a time — is stored; Google Calendar owns the actual time).
- **Push notifications + Add to Home Screen** (not in the original blueprint — added post-launch-prep) — real Web Push, not a stub, plus an install prompt shown to every phone, not just iPhone. `/manifest.json` + `public/sw.js` make the app installable; `src/components/PushNotifications.tsx` (mounted in both the Coach and client Portal shells — `src/app/coach/layout.tsx`, `src/app/portal/layout.tsx`) shows two independent banners, install taking priority when both apply. The install banner targets any phone not already running as an installed app: on Android/Chrome it uses the browser's real native `beforeinstallprompt` prompt when offered, falling back to "open your menu and tap Add to Home Screen" instructions where that event never fires; on iOS (no programmatic install API exists there) it's always the manual Share-icon instructions. The notifications banner offers "Enable Notifications" once a device both supports push and (on iOS specifically) has actually been installed — Apple only allows Web Push from the installed app, not Safari itself, so it never offers a button there that would silently fail. Subscriptions are stored in `push_subscriptions` (`src/lib/repo/pushSubscriptions.ts`) and sent via `src/lib/webPush.ts` (falls back to a silent no-op, same `*_CONFIGURED`-flag pattern as Stripe/Resend, until `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` are set — see "Before this goes live"); a 404/410 from the push service (subscription gone) is treated as cleanup, not an error. Client pushes ride the same hook every client-facing email already goes through (`sendEmailDraft`/`sendSystemEmail` in `src/lib/email.ts`), so meeting reminders, plan-ready, account invitations, and every other client email also fire a push with no per-template wiring needed. Coach pushes are explicit calls at the two moments Journey asked for: a new application (`src/app/apply/actions.ts`) and a payment received (Foundation fee in `src/lib/checkout.ts`, Accountability enrollment in `src/lib/accountability.ts`).
- **Brand mark, used everywhere** — the circle/"S"/leaves monogram now actually exists in the app, not just the color palette and fonts (which already matched — `src/app/globals.css`'s six brand tokens are exact hex matches for the brand guide's palette). It's sourced from Journey's real logo files (`public/brand/source/` — actual exports from the design file, not hand-traced or AI-generated), with the near-solid background chroma-keyed out to make two reusable transparent PNGs: `public/brand/mark-on-light.png` (dark-green ink, for light backgrounds) and `public/brand/mark-on-dark.png` (cream ink, cropped from the "stacked on dark" export). `src/components/BrandMark.tsx` renders the light version next to the "Steadwell" wordmark on the landing page and in both the Coach and Portal headers. The dark version, composited onto this app's actual `--brand-dark` token, replaced the generic default Next.js favicon and is what the PWA home-screen icons (`public/icon-192.png`, `public/icon-512.png`, `public/apple-touch-icon.png`, `src/app/favicon.ico`) actually show now, instead of a plain letter in a box. `scripts/generate-icons.py` is how all of this was generated from the source files, and is the way to regenerate it if Journey supplies new/updated logo files.
- **Attention Queue, account lockout, backups, and validation hardening** (§11, §14) — the last build-order step, closing out the app with real polish rather than a placeholder page. The Coach Dashboard's old "Needs Attention" stub (`src/lib/attentionQueue.ts`) is now the real thing: applications awaiting Review or Payment, Foundation Intakes ready for Plan Build, account invitations that are expired or expiring soon, payments stuck pending long enough to look failed, and clients who reopened a submitted intake to make a correction — six categories, every one backed by a real query, not sample data. **Account lockout** (`src/lib/repo/users.ts`) locks a user out for 15 minutes after 5 failed password or 2FA attempts on either the coach or client login flow — a real brute-force guard, not just a rate-limit comment. **Backups** (`/coach/backup`, `src/lib/backup.ts`) is a genuine on-demand export of every table in the database as one JSON file. It's also the shared core of the real automated nightly backup added later — see the "Before this goes live" bullet below. **Validation hardening** (`src/lib/formHelpers.ts`) replaced the ad hoc `Number.isFinite(x) ? x : 0` / `String(x).trim()` pattern duplicated across every Foundation Intake and Plan Builder form with shared helpers that also cap money fields at a sane ceiling and free-text fields at a sane length — real server-side bounds, not just client-side `<input>` hints.
- **Forgot-password** (§2, not in the original blueprint's numbered build order — added post-launch-prep alongside push notifications) — `/forgot-password` → emailed single-use link → `/reset-password/[token]`, for both roles. See the "Before this goes live" bullet below for the full detail (it's a small enough addition that it's documented once, not twice).
- **Automated off-site backups** (§14, extending the on-demand backup above — added post-launch-prep once the production database turned out to be on Supabase's Free plan, which takes no backups of its own) — a nightly Vercel Cron job gzips a full database export and stores it in Blob storage, pruning down to the most recent 14 nightly snapshots. See the "Before this goes live" bullet below for the full detail.
- **In-app 2-way messaging + "Need help?"** (not in the original blueprint — added post-launch-prep at Journey's request) — a real message thread per client, not a stub. `/portal/messages` (client) and `/coach/messages` + `/coach/clients/[id]/messages` (coach) share one `messages` table (`src/lib/db/schema.sql`) and repo layer (`src/lib/repo/messages.ts`). The client Portal header always shows a "Need help?" icon (badged with the unread count) that goes straight to their thread — the whole point is it's one tap away, not buried in the nav. Sending a message fires a push notification immediately (same `*_CONFIGURED`-gated `webPush.ts` used everywhere else) plus, for a client-to-coach message, an email to Journey too, since a coach might not have the app open (`src/lib/messages.ts` — `sendClientMessage`/`sendCoachMessage`). Opening a thread marks the other party's messages read (both thread pages call `markThreadRead` during render — safe because these routes are always dynamic/auth-gated, never statically cached). The Coach inbox (`/coach/messages`) lists every client with a conversation, most recently active first, each with its own unread badge; the client's detail page also shows a message count + unread badge so Coach doesn't have to leave the client record to notice a new message. Both nav headers show a badge on "Messages" with the coach's/that client's unread count. **A client can also attach a file** (PDF, image, or Word/Excel — 10MB cap) to a message, uploaded to the same private Vercel Blob storage Statements uses (`messages.attachment_url`/`attachment_filename`/`attachment_content_type`, nullable — see the schema.sql comment on why this isn't just reused as a Statement, which needs an account/month it doesn't have). Downloads go through `/api/messages/[id]/attachment`, the same ownership-checked pattern as `/api/statements/[id]/download`. A file-only message (no caption) is allowed — the compose box's text field isn't required when a file is attached. Every attachment also shows up on the client's real Documents page (`/portal/documents` — previously a placeholder), alongside their Statements, as a standing "everything I've sent Steadwell" reference list — and, in the Plan Builder's Stage 1 Baseline panel, alongside Statements there too, so Coach can review whatever a client sent without hunting through the message thread. **Coach can attach a file to a reply too** — the same upload/validation path, extracted into a shared helper (`src/lib/messageAttachments.ts`) used by both the client's compose action and Coach's reply action so the two sides can't quietly drift (e.g. one accepting a file type the other rejects); a coach-sent attachment downloads through the same ownership-checked `/api/messages/[id]/attachment` route and shows up on the client's Documents page exactly like a client-sent one.
- **Responsive collapsible nav** (fixed post-launch-prep — the old horizontal-only Coach/Portal nav overflowed and clipped "Sign out" on real phones) — `src/components/NavHeader.tsx` is a shared client component used by both `src/app/coach/layout.tsx` and `src/app/portal/layout.tsx`: a normal horizontal nav on desktop widths, collapsing on mobile to a hamburger button that opens a fixed-position panel overlapping the page (with a dismiss-on-click backdrop) instead of trying to squeeze every link into one row. Verified against a real mobile viewport (390×844) with Playwright, logged in as both roles, in both the closed and open states.
- **Delete Client Permanently** (added post-launch-prep — an admin escape hatch for a client record that's stuck, a broken test signup, or a duplicate, not part of the blueprint's §16 offboarding flow) — a "Danger Zone" card on the Coach's client detail page (`src/app/coach/(protected)/clients/[id]/DeleteClientForm.tsx`), gated behind typing the client's exact full name (checked server-side too, not just disabling the button). Runs the same real `hardDeleteClient` the normal 30-day sweep eventually would (`deleteClientImmediately`, `src/lib/offboarding.ts`) — immediately, and reuses the same `offboardings` row as its audit tombstone, so this is a faster path to the same end state, not a separate/lesser deletion. Building this surfaced and fixed two real gaps in the existing hard-delete: the new `messages` table (added alongside in-app messaging above) wasn't in the child-table cleanup list, so a hard-deleted client's message thread would have silently survived; and `push_subscriptions` has no `ON DELETE CASCADE` on its `users` foreign key, so deleting a client's user account would have thrown a foreign-key violation (rolling back the whole delete) for any client whose device had push notifications enabled — both fixed in `src/lib/repo/deletion.ts`. Verified against real Postgres: a client with a push subscription and messages actually gets fully cleaned up with no FK error, and calling this on a client already mid-30-day-countdown (an existing `offboardings` row) doesn't crash on the table's `UNIQUE` constraint.
- **Multi-coach / Owner roles, self-service coach invites, and Revenue Reports** (added post-launch-prep at Journey's request — "if I were to hire a coach down the road, how can I make them a coach account") — the single-coach assumption baked into every earlier bullet above is gone. There are now two coach-side roles sharing the same `/coach/*` login and app: **owner** (Journey/Boldly Built — sees and can act on every client, plus the two owner-only areas below) and **coach** (a hired coach — sees and can act only on clients assigned to them). `clients.coach_id` (nullable) records the assignment; `src/lib/dal.ts`'s `requireClientAccess(clientId)` is the single access check every `/coach/clients/[id]/**` page and action now calls instead of a bare role check — owner unrestricted, a coach gets `notFound()` (not a 403) on a client that isn't theirs, so probing another coach's client id can't even distinguish "not yours" from "doesn't exist." The Coach Dashboard, Clients list, Messages inbox, and unread-message badge are all scoped the same way (`listClients`, `getAttentionQueue`, `listThreadSummariesForCoach`, `countUnreadForCoach` all take an optional `coachId`). A hired coach can't reach Delete Client, Backups, the Offboarding sweep button, Discount Codes, or Booking Links — those stay behind a new `requireOwner()` gate (`src/lib/dal.ts`) even for a coach acting on their own assigned client. **Team page** (`/coach/team`, owner-only) — enter a name + email, the app emails a secure single-use invite link (`coach_invitations` table, same 7-day-token shape as the existing client invite flow); the invited coach sets their own password and 2FA at `/invite/coach/[token]` — the owner never sees or sets it. The Team page also lists the current roster **by name, not email** (`users.full_name` — a coach invite's name now carries over onto the account it creates on accept; the owner account, and anyone invited before this, gets an inline "Set Name"/"Update Name" field right on the roster row since nothing collected one for them) and lets the owner flag one coach **Default Coach** (`users.is_default_coach`, at most one at a time); new public applications (`src/app/apply/actions.ts`) auto-assign to whichever coach is currently flagged default, and **any coach-side user can reassign one of their own clients** to a different coach (or unassign) from a "Coach" card on that client's detail page — originally owner-only, relaxed at Journey's request ("I want coaches to be able to reassign clients to other coaches") since `reassignClientCoach` (`src/app/coach/(protected)/clients/[id]/actions.ts`) already runs behind `requireClientAccess(clientId)`, which confines a non-owner coach to clients actually assigned to them — there's no additional "must be a real coach" check on the target beyond what the `<Select>` on the page offers, so reassigning to yourself is just a harmless no-op. **Revenue Reports** (`/coach/reports`, owner-only, `src/lib/repo/reports.ts`) — total Foundation-fee revenue collected (all-time + this month), Active Subscriptions/MRR by Accountability tier, revenue by coach (Foundation fees collected + current MRR from each coach's assigned clients), and discount-code impact (redemptions, amount collected, amount estimated given up). Honestly scoped, not overclaimed: this app never receives Stripe's `invoice.paid` webhook, so there's no local record of what's actually been collected on a recurring Accountability subscription over time — "Total Revenue Collected" is Foundation fees only, and Accountability shows as a live MRR projection instead (see the comment at the top of `src/lib/repo/reports.ts`). The one-time production migration that promotes the existing single coach account to `owner` (`schema.sql`, deliberately scoped to that one known email rather than a blanket `WHERE role = 'coach'` — see the comment there) also removed a legacy `src/app/api/setup/seed-coach` backdoor route that created `coach`-role accounts given only `CRON_SECRET` as a URL query param, now superseded by the real invite flow above. Verified against real Postgres — schema migration (`users_role_check` widened, `coach_invitations` table, `is_default_coach`/`coach_id` columns), cross-coach data scoping (`listClients`/`getAttentionQueue`), default-coach reassignment, new-application auto-assignment, the full invite-create → resend → accept lifecycle, and Revenue Reports' four numbers all reconciling exactly against inserted test payments/subscriptions — see git history for the verification script (not kept in the repo; it created and cleaned up its own test rows).
- **Coach commission invoicing** (added post-launch-prep at Journey's request — "the 1099 coach [should] be able to conveniently bill Steadwell for their cut of proceeds from their clients," their rate "assigned at the owner level at the coach account creation") — a hired coach's 1099 commission rate (`users.commission_percent`, 0–100) is required on the Team page's "Invite a Coach" form going forward and carries over automatically to the `users` row on invite acceptance (same pattern as `full_name`); the owner can also backfill or edit it later via an inline "Set %"/"Update %" field on each coach's Team page row. **Billing is deliberately based only on money actually collected, never a live projection** — Journey's explicit constraint: "foundations plus paid accountability months. if the client doesnt pay, they dont get paid and arent obligated to do any work for them." Foundation fees already have a real `status = 'paid'` signal (`payments` table); Accountability didn't (this app has never received Stripe's `invoice.payment_succeeded` event before now — see the honesty-gap comment at the top of `src/lib/repo/reports.ts`), so a new `accountability_payments` table is the real ledger of Accountability revenue actually collected, one row per successful charge. It's populated two ways: the real Stripe webhook, `invoice.payment_succeeded` (`src/app/api/webhooks/stripe/route.ts`), for every real renewal — idempotent via a `UNIQUE` constraint on `stripe_invoice_id` with `ON CONFLICT DO NOTHING`, so a Stripe retry can't double-record a charge this app already processed (Postgres treats multiple `NULL`s as non-conflicting, which is what makes this a no-op guard specifically for real, non-null Stripe invoice ids); and `fulfillAccountabilityEnrollment` (`src/lib/accountability.ts`), for exactly one test-mode row at the moment of enrollment when there's no real Stripe subscription behind it — explicitly not simulating ongoing monthly renewals, since there's no local billing clock to drive those. (Note: this Stripe API version nests the invoice's generating subscription under `invoice.parent.subscription_details.subscription` rather than a removed top-level `invoice.subscription` field — found by checking the pinned `stripe` SDK's own `.d.ts`, not assumed.) A coach generates their own invoice self-service at `/coach/billing` (`src/app/coach/(protected)/billing/`, gated by `requireCoach()` — any coach-side user, not owner-only, since this is a coach billing *for themselves*): it snapshots every currently-uninvoiced Foundation fee and Accountability payment for their assigned clients into one `coach_invoices` row, with one `coach_invoice_items` row per included payment (`src/lib/repo/coachInvoices.ts`, wrapped in a real transaction so a failure partway through can't half-write it). A `UNIQUE` index on `coach_invoice_items(source_type, source_id)` is the double-billing guard — generating an invoice only ever selects payments with no existing item row (`NOT EXISTS`), so the same payment can never land on two invoices; `commission_percent` is snapshotted onto the invoice at generation time, so a rate change later never rewrites a past invoice. Each invoice downloads as a real PDF (`src/lib/coachInvoicePdf.ts`, reusing the existing `pdfkit` chunks/`end`-event pattern from `src/lib/dataExport.ts` — no new dependency) via `/api/coach-invoices/[id]/pdf`, itemized by client and grouped Foundation vs. Accountability, gated the same way `requireClientAccess` gates a client record: the owner can reach any invoice, a coach only their own (`notFound()`, not a 403, on someone else's). Status is tracked in-app, Pending → Paid (`coach_invoices.status`/`paid_at`) — no in-app payout rail, just the record — settable only by the owner from a new **Coach Invoices** section on `/coach/reports` (`markCoachInvoicePaidAction`), which lists every coach's invoices with a PDF link and a "Mark Paid" button. Verified against real Postgres: commission-percent round-trip through `createUser`/`setUserCommissionPercent`/a coach invitation, `recordAccountabilityPayment` idempotency under a repeated `stripe_invoice_id`, both uninvoiced-payment queries correctly excluding what's already been billed, a full invoice generation producing exactly the expected commission totals (verified against a known dollar amount and rate) and correctly removing its items from both "uninvoiced" queries so they can never reappear on a second invoice, and `markCoachInvoicePaid` — see git history for the verification script (not kept in the repo; it created and cleaned up its own test rows).

## What's a dev stand-in (clearly labeled in the UI)

- Emails are never actually sent — accepted/declined/invite emails are drafted, shown to the coach to edit, and "sending" just logs them and marks them Sent in the database. There's no SMTP provider wired up.
- Stripe checkout runs in test mode until you configure it — see above. That's a configuration gap, not a fake implementation; the code path it falls back to is a UI stand-in, but the code it *would* run instead is real.
- **Foundation Intake → Statements** (`/portal/foundation/statements`) is real — clients upload real files to Vercel Blob (private access; see `src/app/api/statements/[id]/download/route.ts`), Coach sees them all on each client's detail page. Requires `BLOB_READ_WRITE_TOKEN` — see "Before this goes live" below.
- **"Request an Update" reopens the whole intake, not just one section.** The blueprint's fuller spec is per-section unlock (so a correction to one section can't silently reopen an already-reviewed section). Documented in `src/lib/repo/foundationIntake.ts`; worth building once Plan Build (§5) exists and there's a real notion of "which sections Coach has already used."
- **Account lockout is per-account, not per-IP.** There's no shared rate-limit store (no Redis) in this dev environment to key a lock on IP address across requests, so 5 failed attempts locks the *account* for 15 minutes regardless of where the attempts came from. A real production deployment should add IP-based limiting too — the two aren't mutually exclusive. Documented in `src/lib/repo/users.ts`.
- **The Attention Queue's "failed payment" category is inferred, not reported.** Stripe's webhook only tells this app about a *successful* checkout (`checkout.session.completed`); a declined card or an abandoned checkout leaves the payment row at `status: 'pending'` forever, with no event to flip it to `'failed'`. So this category is really "payment stuck pending for over 24 hours" — a reasonable proxy, but a real launch should also listen for `checkout.session.expired` / `payment_intent.payment_failed` to get a genuine failed status. Documented in `src/lib/repo/payments.ts`. The Attention Queue also has no missing-statement category yet — real Statements data exists now (see above), this just hasn't been built on top of it.
- **Validation hardening (`src/lib/formHelpers.ts`) is a bounds-and-length pass, not a schema rewrite.** It replaced hand-rolled `Number.isFinite`/`.trim()` calls with shared helpers that clamp money fields to a sane ceiling and cap free text at a sane length — real server-side validation, but lighter-weight than the one form that already uses full `zod` validation (the public application, `src/app/apply/actions.ts`). Porting every Foundation Intake/Plan Builder form onto `zod` the same way is a reasonable next step, not required for this to be genuine validation.

## Why this stack

- **Next.js 16 (App Router, Turbopack) + TypeScript + Tailwind v4** — standard, well-supported choice for this kind of app.
- **`node:sqlite`** (Node 22's built-in SQLite driver) instead of Postgres/Prisma for local dev — zero setup, one file (`data/steadwell.db`), no native binaries to install. The schema (`src/lib/db/schema.sql`) deliberately avoids SQLite-specific features (native enums, etc.) so migrating to Postgres later is a schema-translation exercise, not a redesign. **This is not what you should run production on** — see "Before this goes live" below.
- **`iron-session`** for stateless, cookie-based sessions (no session-store server to run).
- **`otpauth` + `qrcode`** for standards-based TOTP 2FA — works with any authenticator app.
- **Self-hosted fonts (`@fontsource`)** instead of Google Fonts' CDN, so the app has zero external font dependency at build or runtime.
- **`pdfkit`** (pure JS, no native deps) to generate the client's plan PDF on demand from finalized, immutable plan data — see the Plan Builder bullet above.

## Running it locally

```bash
npm install
npm run dev
```

Open http://localhost:3000. The database and its schema are created automatically on first use, at `data/steadwell.db`.

To create the one Coach account:

```bash
npm run seed
```

This prints a generated password once — save it, it's not stored anywhere else (only its bcrypt hash is). Re-running `npm run seed` after the account exists is a no-op. Delete `data/steadwell.db` (or the whole `data/` folder) any time you want to start over from an empty database.

### Running the smoke test

`scripts/smoke.ts` drives a real headless browser (Playwright) through the entire working pipeline end to end: submit an application → coach logs in and sets up 2FA → coach approves and enables a discount code → client accepts the agreement, applies the discount, and pays (test mode) → coach sends the account invitation → **the invitation is backdated into its expiring-soon window and the Coach Dashboard's Attention Queue is checked for it** → client accepts the invite, verifies email, sets up 2FA → client fills out and submits Foundation Intake (including the zero-Goals validation error, the income-normalization math, and the read-only lock / Request-an-Update cycle — **checking the Attention Queue shows the client under "Correction Requested" while the intake is reopened, then under "Ready for Plan Build" once resubmitted**) → coach builds a real plan through every Plan Builder stage (Baseline, Cash-Flow Allocation, Debt Strategy, Savings & Goals, Stress Test, Finalize — including the balance check, First-30-Days action items, Mark Reviewed, Finalize Plan, and Present Plan to Client) → client sees the real finalized plan in the portal and downloads the real PDF → client enrolls in Accountability (test mode) → coach logs a meeting → client sees the meeting's action items on their Accountability page but not Coach's private notes → client changes tier, checks Billing, then cancels Accountability, landing on the same 30-day-countdown screen the Graduated path uses (a second, distinct Offboarding trigger — see §16) → **the offboarding record is backdated directly in the DB (real time can't be fast-forwarded in a live test) and the Coach Dashboard's "Run Sweep Now" button is driven to exercise the real reminder sweep** (asserting the email auto-sent with no draft/review step, and `remindersSent` incremented) → client downloads the real data-export PDF and the test confirms reminders correctly stop afterward → the deletion date is backdated and the sweep is run again to exercise the real hard-delete job, asserting the client's financial data is actually gone and the `clients` row is anonymized rather than deleted → **five wrong passwords in a row lock the coach account, a sixth attempt with the *correct* password is still rejected, the lock is cleared directly in the DB, and a normal login is confirmed to work again** → **the coach downloads the full JSON backup and the test asserts every expected table is present and non-empty**. It asserts on real page content, real computed prices, real computed plan math, and real database state at each step, not just HTTP status codes.

```bash
npm run build
APP_URL=http://localhost:3100 npm run start -- -p 3100    # run in a second terminal, or backgrounded
npm run seed                   # note the printed password
SEED_COACH_PASSWORD='<printed password>' BASE_URL=http://localhost:3100 npm run smoke
```

`APP_URL` matters here, not just `BASE_URL` — it's what the server itself uses to build links it emails out (the agreement link, invite link, export link), so it has to match whatever port you're actually serving on or the smoke test's `page.goto()` calls will hit connection-refused following a link built for the wrong port.

The response is identical whether or not an account exists for that email, so the form can't be used to check who has a Steadwell login. Completing a reset also clears the account's failed-login lockout (§14) — proving control of the inbox is a legitimate way back in, not just a 15-minute wait. The one email in the app not sent through the usual client-scoped `email_logs`/`sendEmailDraft` pipeline — a coach account has no `clients` row to look the address up through — so `sendPasswordResetEmail` in `src/lib/email.ts` calls the shared `deliver()` helper directly; nothing to log to `email_logs` for it and no push (a coach has no `client.userId` either). Same `RESEND_CONFIGURED`-gated dev-mode convenience as elsewhere: without a real `RESEND_API_KEY`, the confirmation screen shows the reset link directly instead of only console-logging it.
9. ~~Real cron infrastructure for the Offboarding sweeps~~ **Wired up, needs a schedule to actually run.** `src/app/api/cron/offboarding-sweep/route.ts` is a real, secret-protected route (`Authorization: Bearer <CRON_SECRET>`) that calls `runReminderSweep`/`runDeletionSweep`; `vercel.json` points Vercel Cron at it daily (13:00 UTC — adjust if you want a different time). Set `CRON_SECRET` to the same value in both `.env` and your hosting platform's env vars. The Coach Dashboard's "Run Sweep Now" button still works too, for manual/demo use. The BIRTHDAY20 daily sweep (`runBirthdayDiscountSweep`, see the Discount codes bullet above) rides along on this same route and schedule rather than getting its own Vercel Cron entry — its own manual "Run Now" button lives on `/coach/settings/discount-codes` instead. The Accountability meeting-notes reminder sweep (`runMeetingReminderSweep`, see the Meetings bullet above) rides along here too; its manual trigger is folded into the Coach Dashboard's existing "Run Sweep Now" button.
10. ~~Real automated backups, on a schedule, stored off-site~~ **Done.** `src/app/api/cron/db-backup/route.ts` runs nightly via Vercel Cron (`vercel.json`, 08:00 UTC — a distinct time from the Offboarding sweep's 13:00 UTC, since Hobby-plan cron jobs are limited to once/day each) and calls `runAutomatedBackup()` (`src/lib/backup.ts`), which reuses the same `buildFullBackup()` as the on-demand `/coach/backup` export (§14), gzips it, and stores it in the same private Vercel Blob store already used for Statements uploads — pruned to the most recent 14 nightly snapshots (~2 weeks) after every run, sorted by actual upload time rather than filename. This exists specifically because our production database is on Supabase's **Free** plan, which takes no backups of its own — Supabase's own docs recommend exactly this pattern (regular exports + off-site storage) for Free-tier projects. If you ever upgrade to a paid Supabase plan with its own managed daily backups, this becomes redundant-but-harmless belt-and-suspenders rather than the only safety net. Restoring from a snapshot is a deliberate manual admin task (download the `.json.gz` from Blob, gunzip, re-insert per table) — there's no self-service restore UI, since this is meant to be an emergency-only path, not a routine feature.
11. ~~Encryption at rest for the database~~ **Confirmed.** Supabase encrypts all data at rest by default on every plan, including Free — AES-256, always on, not something that needs configuring or can be turned off. HTTPS in production (which Vercel gives you by default) covers transit. §2's "encrypt financial documents in transit/at rest" is a checked fact for the current setup, not an assumption — if you ever move providers, re-confirm the same thing for whichever one you land on.
12. **IP-based rate limiting to complement the new account lockout.** `src/lib/repo/users.ts` locks an *account* after 5 failed attempts (§14) — a real, working guard — but it has no per-IP dimension. A production deployment should add IP-based limiting on top (Vercel's own Firewall/rate-limiting, or a shared store like Upstash Redis), so an attacker can't spread guesses across many accounts to dodge the per-account lock.
13. **A fuller `zod` validation pass.** The Foundation Intake and Plan Builder forms clamp money fields and cap text length server-side (`src/lib/formHelpers.ts`, §14) — real bounds, not just UI hints — but only the public application (`src/app/apply/actions.ts`) has full schema-shaped validation with per-field error messages. Porting the rest onto `zod` the same way is a reasonable next step.
14. ~~Turn on push notifications~~ **Done.** `VAPID_PUBLIC_KEY` and `VAPID_PRIVATE_KEY` are set in Vercel's Production environment, so `PUSH_CONFIGURED` (§ "What's actually real") is true on the live site. `VAPID_SUBJECT` is optional and defaults to a `mailto:` address if unset.

## Two bugs this smoke test caught (worth knowing about)

Both are fixed, but they're worth knowing if you extend this app:

- **A layout can't redirect to a page nested inside itself.** `coach/layout.tsx` and `portal/layout.tsx` originally redirected to their own 2FA setup page when 2FA wasn't enabled yet — but that setup page was rendered *through* the same layout, so the redirect target immediately re-triggered the same redirect, forever. Fixed with Next's route groups: the strict "you must have 2FA enabled" check lives in `coach/(protected)/layout.tsx` / `portal/(protected)/layout.tsx`, applied to everything except the setup-2fa page itself, which stays outside that group.
- **A generic `button[type="submit"]` selector isn't safe on a page with a "Sign out" button in the header.** Both the coach and client authenticated layouts have a "Sign out" button with `type="submit"`, which appears earlier in the page than the real form's submit button — so a Playwright test (or a keyboard "Enter" in the wrong field, in theory) can trigger the wrong form entirely. If you write more tests against these pages, scope your selectors to the specific button text, not just its type.
- **A CSS `uppercase` class changes what Playwright's `innerText()` returns.** The discount-code status label is styled uppercase in CSS; the *rendered* text Playwright reads back is "ENABLED", not the DOM's actual "Enabled" — `innerText()` reflects applied styles, not markup. Match case-insensitively (or against the raw label) if you're asserting on text that has any text-transform applied to it. (This bit again on the Stress Test page's "SHORTFALL" label.)
- **A same-URL Server Action redirect can leave the DOM mid-swap when a second interaction follows immediately.** On the Cash-Flow Allocation page, saving the Emergency Fund amount and then immediately filling and saving the Sinking Fund amount — both server actions that redirect back to the same URL — silently saved `0` for the sinking fund even though `inputValue()` read the just-typed value correctly right before the click. `waitForLoadState("networkidle")` can resolve a beat before React finishes patching the DOM with the post-redirect data, so a second Playwright locator (which re-resolves lazily) can land on a stale node that's about to be replaced. Fixed by doing a full `page.goto(sameUrl)` between sequential same-page saves instead of trusting `waitForLoadState` alone — a real fresh navigation, not a soft transition. The same class of staleness also showed up reading `body.innerText()` right after a same-URL redirect (e.g. immediately after clicking "Finalize Plan"); `scripts/smoke.ts`'s `waitForBodyText()` helper polls for the expected text instead of reading once.
- **`body.innerText()` never includes a form field's value — only its rendered text content.** Checking that a just-saved Meeting's notes "showed up" by searching `body.innerText()` for the text always failed, even with fresh DOM — `<textarea>`/`<input>` values are DOM properties, not part of the accessibility-tree text `innerText()` walks, so they're invisible to it regardless of staleness. Read a form field back with `locator(...).inputValue()` instead; `innerText()` is only for content actually rendered as text (like the client-facing `<p>` that shows a meeting's action items on `/portal/accountability` — that one works fine with `innerText()` since it's not a form control).
